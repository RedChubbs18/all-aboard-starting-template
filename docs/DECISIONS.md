# Decisions

| D1 | Stack | Next.js + TypeScript + Tailwind + MSAL + Prisma/SQLite, Vitest (brief default). | 2026-11-09 |
| D2 | AI provider (FR-1.7, FR-3.12) | Claude via the Anthropic API behind `ChatbotAdapter` and `PhotoCheckAdapter`. The key lives only in local `.env` as `ANTHROPIC_API_KEY`, server-side only. The mock stays the default and is the demo fallback. | 2026-11-09 |
| D3 | Chase LM trigger (FR-MI.3) | Offer a chase when any LM-owned task is past its due date and not DONE. **Clarification:** "overdue" has one definition, `isOverdue(task, now, tasks)` in `src/domain/engine.ts`, used by `progress()`, the LM list and MI (issues and chase): an applicable, non-optional task that is not effectively done (a DONE override such as `photo-check-override` counts as done for `photo-check-passed`), is not LOCKED (it is waiting on something else), and whose due date is before today: overdue from the day after the due date (UTC day compare, `isPastDue` in `src/domain/stage-timing.ts`, also used by the starter view in `src/components/journey/format.ts`), so a task due today is not overdue. | 2026-11-09 |
| D4 | Hosting | Run locally for the demo. Mobile access and PWA install go through an HTTPS tunnel. That tunnel URL must be added as an Entra SPA redirect URI. No Azure hosting spend. | 2026-11-09 |
| D5 | Git | Commit and push freely to the fork. Run a secret scan before every push. | 2026-11-09 |
| D6 | Roles | Roles are stored in the app DB, keyed by Entra `oid`, not Entra app roles. That way the admin UI (FR-AD.3) can manage them. | 2026-11-09 |
| D8 | AI model | `claude-opus-5-5` at effort `low` for both the chatbot and the photo check. Uses structured outputs and prompt-caches the FAQ corpus. Server-side refusal fallbacks (`fallbacks: "default"`) are on. If the API errors or there's no key, it falls back to the mock. | 2026-11-09 |
| D9 | PEV provider | Pre-employment vetting uses **First Advantage**, not HireView. User-facing text says First Advantage. The code identifiers (`hireview` adapter key, `hireviewStatus`) are renamed to `firstadvantage` in one sweep after integration. | 2026-11-09 |
| D10 | Stage meanings | Conditional offer: the colleague has accepted the role. Vetting (PEV): the colleague has received the First Advantage request to enter their vetting information. Unconditional offer: PEV is complete **and** all other offer conditions are met (new gating task `offer-conditions-met`, owned by P&P). Day 0: first day. Day 30: day 30 onwards. A First Advantage "cleared" result alone must not advance the stage; it completes the vetting task, and the stage advances when all PEV gating tasks are done. | 2026-11-09 |
| D11 | Colleague File ID | Generated automatically by SailPoint (IAM), so adapterKey is `sailpoint`, not Workday. | 2026-11-09 |
| D12 | Photo recertification | Both P&P and the starter's LM can override (recertify) a rejected pass photo. | 2026-11-09 |
| D13 | Offer-to-start gap | Can be up to 3 months. Due dates are computed from the start date and clamped so none falls before the journey was created (offer acceptance) plus a small grace period. | 2026-11-09 |
| D14 | Exit reasons | Wherever possible the reason comes from the colleague. A starter can withdraw from the app, choosing a reason category and optionally adding a short comment (with a warning not to include personal details). Categories: `ACCEPTED_ANOTHER_OFFER, ROLE_NOT_RIGHT, PERSONAL_CIRCUMSTANCES, PAY_OR_BENEFITS, LOCATION_OR_HYBRID, ONBOARDING_EXPERIENCE, PREFER_NOT_TO_SAY, OTHER`, plus P&P-recorded `FAILED_PEV, OFFER_WITHDRAWN_BY_LBG, NO_SHOW`. Also stored: who supplied the reason (COLLEAGUE or PNP). | 2026-11-09 |
| D15 | Buddy | Buddies sign in with their own access. They get a read-only view of their starter, plus a chat link, and can complete BUDDY-owned tasks only. | 2026-11-09 |
| D16 | Visual style | Follow `docs/STYLE.md` (team-supplied guide). Its section A records the contrast fixes (deep green for small green text, a darker "Shared" pill, a dual-colour focus ring, readable disabled text), the 430px column for starter screens with wider LM/MI/admin layouts, the "Your bank" logo placeholder, and the original horse kept in the marker. |  2026-11-09 |
| D17 | Epture → Eptura Engage (FR-3.10) | Eptura Engage is the internal desk and meeting room booking tool. The template `eptura-engage-access` is a SYSTEM task, with content page `eptura-engage` and FAQ faq-17. Sticky-note colours on the board are ignored, per the team. | 2026-11-09 |
| D18 | Official branding | The internal branding team has given permission to use the official Lloyds branding. The official logo and horse mark (cropped from the same SVG, not redrawn) come from lloydsbank.com and live in `public/brand/official/`. The team confirmed the assets may be committed to this public repo, because they are already publicly available. The app reads `NEXT_PUBLIC_BRAND_ASSETS=official` to use them, and falls back to the placeholders otherwise. GT Ultra (Median and Standard, Regular and Bold, WOFF2) was supplied by the team and lives only locally in `public/fonts/`, which is git-ignored. Font licences forbid redistribution, so the files are never committed to this public repo. Fresh clones fall back to the STYLE.md stack. | 2026-11-09 |
| D19 | Graph guest invite (F1) | Real Entra B2B invite via Microsoft Graph `POST /invitations`. **Updated 2026-11-10 (team decision):** the delegated recruiter sign-in (MSAL in the browser) is replaced, for the demo-only mock Workday, by an app-only server-side invite: a separate confidential app registration `team05-mock-workday` with the Application permission `User.Invite.All` (admin consent) and a short-lived client secret kept only in the local git-ignored `.env` (delete it after the event). MyJourney itself still has no Graph secret. Original design: delegated `User.Invite.All` from the admin's browser through MSAL. `sendInvitationMessage: true`: Entra sends its own standard invitation email, with a short welcome line, to the address typed at demo time (never stored, confirmed in a dialog first). No custom email, no `Mail.Send`, no mailbox guard. **The organisers' approval is required for external invite emails** (the rule "no email outside the tenant" is waived only by them), so real sending needs `NEXT_PUBLIC_GRAPH_INVITES=on` and `NEXT_PUBLIC_GRAPH_INVITE_EXTERNAL_APPROVED=yes` (mock Workday: server env `GRAPH_INVITE_EXTERNAL_APPROVED=yes` plus the `WORKDAY_GRAPH_*` credentials); otherwise it falls back to the mock with an on-screen reason and an audit Event. Guest display names follow `team05-<name>`; clean them up before 13 Nov. Consent for `User.Invite.All` must come from the organisers; until then it falls back to the mock. | 2026-11-09 |
| D20 | Starter task visibility (F2) | Starters see their own tasks, plus a compact read-only status for SYSTEM steps. LM, BUDDY and P&P tasks are hidden from them. | 2026-11-09 |
| D21 | Checklist lock (F8) | The goals page (Checklist tab) is read-only, with lock icons, until the start date. | 2026-11-09 |
| D22 | Buddy view (F16) | The buddy sees their own BUDDY tasks, plus the starter's name, stage, progress % and a chat link. No starter task detail. | 2026-11-09 |
| D23 | Product name | The app is called **MyJourney**. | 2026-11-09 |
| D24 | Demo mock Workday | A separate demo-only app in `demo/mock-workday/` on port 3001. A recruiter creates a conditional offer; the candidate accepts with their details; the mock Workday **server** sends the Entra guest invite as part of the accept pipeline, app-only and idempotent per offer (Entra's own email, with MyJourney instructions in the custom message; simulated unless external invites are approved and credentials exist). **Updated 2026-11-10 (team decision): no user signs in to mock Workday**; it is just an injection point for a colleague's name and email. The recruiter console is open but limited to this computer (loopback check, optional `RECRUITER_PIN`); the offer page stays public with its unguessable token. Secret handling as in D19; a signed webhook then creates the starter and journey in MyJourney. Personal email stays in mock Workday's git-ignored store (FR-1.9). Contract: `docs/DEMO-WORKDAY.md`. | 2026-11-09 |

The tenant is configured to accept guests. The real invite email is sent through Entra, to a Gmail address in the demo. | 2026-11-10 |
| D27 | Demo start date | A random Monday within 3 months of offer acceptance, the default in mock Workday's offer form. | 2026-11-10 |

| D29 | Device entitlement | Engineering job family: MacBook Pro M5 Pro or HP EliteBook U7 (high spec). All other job families: MacBook Air M5 or HP EliteBook U5 (standard spec). The job family comes from the Workday offer (`jobFamily`). | 2026-11-10 |
| D30 | Task completion prompts | Pure reading tasks auto-complete on open. Tasks needing action or input ask, in a short dialog, "Is this task complete?", with "Yes, mark as done" or "Not yet, I'll come back to it". | 2026-11-10 |

Use the named greens (racing `#024731`, heritage `#006a4d`, dark `#00864f`, everyday `#11b67a`, bright `#62b34f`, accent `#0be248` with black text, calm `#c7ffc6`), charcoal `#323233`, light grey `#f1f1f1`, black and white, error `#b00`, info `#3373cb`; black-background focus states; GT Ultra Standard and Median. | D39 | Guest to member conversion | **Team decision (2026-11-10):** when a starter reaches UNCONDITIONAL_OFFER, MyJourney converts their Entra B2B guest account into a standard internal member account (Graph beta `convertExternalToInternalMemberUser`; same object id, so the `entraOid` sign-in mapping and all journey data are kept) instead of creating a new account, and emails the new work sign-in name plus a temporary password (must be changed at first sign-in) to their personal address. Server-side, app-only, on the existing MyJourney app registration (Application `User-ConvertToInternal.ReadWrite.All`, `User.Read.All`, `Mail.Send`; admin consent by the organisers). The personal address is read from Graph at that moment and, like the password, is never stored or logged (FR-1.9); the outcome is kept in IntegrationState `identity` (`converted`, `conversion_failed`, `conversion_simulated`). Only `team05-` guests are ever touched. Without `GUEST_CONVERSION=on` and the config it is simulated and shown in the UI. Idempotent, with retry for P&P and Admin. Microsoft does not document whether guest MFA or SSPR registrations carry over, hence the always-temporary password and Authenticator set-up. Beta API: may change. Test accounts only; deleted with the tenant. | 2026-11-10 |
